## Data integrity: a cosmofs defect that lost file writes (v1.0.0 to v1.0.3)

Every release before this one has a defect in cosmofs, the disk
filesystem of an installed system, that can lose a file's writes. When a
compressed part of a file (a record of up to eight 4 KiB blocks) was
written again with data that no longer compressed, the old data stayed
mapped under the new data's checksum. Every later read of that part
failed, and the file's pending writes were dropped. It shows mostly in
large files written in pieces: on v1.0.3, about one in sixteen 12 MB
downloads with `wget` to an installed disk was hit. The live image (which
runs from memory) and `/tmp` (memory) are not affected.

**How to tell whether a file was hit.** The kernel log names the file's
inode and block. Look for it with `dmesg | grep 'no copy matches its
checksum'`, or for `dirty page(s) ... lost: write-back failed`. Reading
such a file fails with an I/O error at the damaged part.

**What upgrading does and does not do.** v1.0.4's kernel fixes the cause:
a block's checksum is put back when its mapping fails (cosmofs invariant
CF16), and a scrub of every other cosmofs write path for the same shape,
a value stored before the operation it describes had succeeded, fixed
the sites it found (CF17). Upgrading does not repair data already lost:
a file that reads with an I/O error has to be restored from another copy.
Until you upgrade, do not write large files to an installed v1.0.3's
disk; fetch the release into `/tmp`, as below.

## Upgrading from v1.0.3

An installed system now moves to a new release in place
(`cosmo-upgrade`, shell completeness S7), and back with `cosmo-upgrade
--rollback`. `SHA256SUMS` is signed with the release key
(`SHA256SUMS.sig`), and `cosmo-upgrade` refuses a release whose
`SHA256SUMS` or any of whose files does not verify. v1.0.3 has no
`cosmo-upgrade` of its own, so the new one comes in a package signed with
the release key, which v1.0.3's `pkg` checks against the key it shipped
with before anything of it runs. On the installed v1.0.3 (x86-64 shown;
AArch64 says `aarch64`), with the release's files served from your
computer:

```text
mkdir /tmp/up && cd /tmp/up
for f in kernel.elf boot.tar cmdline manifest cosmo-upgrade.cpk; do wget -q http://10.0.2.2:8000/cosmoos-x86_64-$f || break; done
wget -q http://10.0.2.2:8000/SHA256SUMS && wget -q http://10.0.2.2:8000/SHA256SUMS.sig
pkg install -n ./cosmoos-x86_64-cosmo-upgrade.cpk    # must print: pkg: installing cosmo-upgrade-1.0.3-123 (2 files)
tar -xf cosmoos-x86_64-cosmo-upgrade.cpk sbin/cosmo-upgrade sbin/cosmo-verify
./sbin/cosmo-upgrade /tmp/up
```

Then reboot, and `pkg update && pkg upgrade`. The guide's
[Upgrading](https://github.com/vkuttyp/CosmoOS/blob/v1.0.4/docs/guide/upgrading.md)
page has the whole procedure, what each refusal looks like, and rolling
back. `cosmo-verify FILE SHA256SUMS SHA256SUMS.sig` checks any file of a
release on an installed v1.0.4.

## Shell completeness

The S track of the [1.1 roadmap](https://github.com/vkuttyp/CosmoOS/blob/v1.0.4/docs/roadmap-1.1.md#s-shell-completeness),
found missing by using an installed system on Parallels Desktop:

- **S1 Network inspection**: `ip a`, `ip link`, `ip r`, `ip neigh`;
  BusyBox `ifconfig`, `route`, `netstat`, `arp` and `hostname`; the
  interface ioctls; `/proc/net/dev`, `route`, `arp`, `tcp` and `udp`;
  the host name from DHCP.
- **S2 Applets**: `more`, `nl`, `od`, `strings`, `rev`, `tac`, `yes`,
  `cal`, `time`, `timeout`, `watch`, `nohup`, `killall`, `pgrep`,
  `pkill`, `pidof`, `install`, `realpath`, `split`, `fold`, `paste`,
  `comm`, `cksum`, `base64`, `unzip`, `bzip2`, `bunzip2`, `xz -d`,
  `unxz`, `zcat`, `mktemp`, `logger` (through a native `syslogd`) and
  `setsid`; `ash` history kept in `/root/.ash_history`.
- **S3 Process tools**: BusyBox `ps`, `top`, `free`, `uptime` and
  `kill -l` over `/proc/<pid>/stat`, `status`, `cwd`, `exe`, `root` and
  `environ`, `/proc/meminfo`, `stat`, `loadavg`, `version` and
  `cpuinfo`.
- **S4 Ownership**: `chown`, `chgrp`, `chroot` and `su`.
- **S5 Power and clock**: `reboot`, `poweroff`, `halt`, `date -s`,
  `hwclock`, `/dev/rtc0`.
- **S6 Mounting**: BusyBox `mount` and `umount`, `/etc/fstab` and
  `mount -a` at boot, `lsblk`, `blkid`, `mkfs.cosmofs`.
- **S7 Updating an installed system**: `cosmo-upgrade`, with rollback and
  a boot set that survives an interruption at any point.

Also since v1.0.3: power-off on AArch64 through PSCI (`poweroff` turns a
Parallels VM off), and a virtio-gpu driver whose screen console follows
the display's size.

## Upgrade tested

`make BUILD=release test-upgrade UPGRADE_SET_TAG=v1.0.4`, run on
2026-10-18 from main `1ec37307`, takes the published v1.0.3 image and the
published v1.0.4 set, each fetched from this page and checked against its
`SHA256SUMS` (v1.0.4's against `SHA256SUMS.sig` and the release key). It
passed on x86-64 (87.2 s) and AArch64 (117.4 s), under QEMU:

- v1.0.3 installs itself on a disk and boots it with the release key.
- On that system, v1.0.3's `pkg install -n` accepts the cosmo-upgrade
  package and refuses it with one byte changed. `cosmo-verify` and
  `cosmo-upgrade` refuse a `kernel.elf` with one byte changed, a
  `SHA256SUMS` with one digest changed and a release without
  `SHA256SUMS.sig`; `cosmo-upgrade` refuses a bad manifest signature, an
  unknown signing key, a changed archive and a loader that does not
  trust the running set's key. The ESP is unchanged byte for byte.
- An upgrade killed after writing, and one killed after switching the
  loader, each leave v1.0.3's set booting.
- `cosmo-upgrade` moves the system to v1.0.4 in about 4 s, keeping the
  operator's files; v1.0.4 boots with the release key; a second
  `cosmo-upgrade` is refused while one runs; `pkg upgrade` works.
- `cosmo-upgrade --rollback` returns to v1.0.3, keeping `/root` and the
  upgraded package, and rolls forward to v1.0.4 again.

v1.0.4's loader is byte for byte v1.0.3's, so the upgrade's loader
switch writes the same file and a rollback has no loader to change.

One mismatch: the package and the kernel name themselves `1.0.3-123`
(`v1.0.3-123-g1ec37307`), not `1.0.4`. The release build read the tag as
a lightweight one, and the build ID skips those. The files are the ones
signed and published here.
