## Boots with any RAM size (4 GB+ machines hung at handover in v1.0.0-v1.0.4)

Every release before this one stops right after the loader's last line,
`jumping to kernel entry ...`, on a machine with 4 GB of memory or more
where the firmware loads the loader above 4 GiB. Parallels Desktop's
default VM (4 GB) is one; v1.0.0 to v1.0.4 needed 2 GB there. The loader
mapped a fixed 4 GiB of physical memory for the handover, and the code
doing the handover was outside it.

The loader now maps everything the kernel needs at entry: all RAM, the
loader itself, the ACPI tables, the framebuffer and the serial console.
When that cannot be done, it says why on the screen and stops before
the handover, instead of hanging. Nothing changes in how the loader and
kernel talk to each other: an installed v1.0.4 upgrades to this release
in place, and the upgrade brings the new loader with it.

Tested: QEMU with 1, 4 and 8 GB on x86-64 and AArch64 (`make
test-platforms`, every change from now on), and Parallels Desktop 27.0.3
with 4 and 8 GB.

Also fixed on machines with more than 4 GiB: a RAM disk, and the kernel's
self-tests, refused buffers above 4 GiB (a 32-bit DMA limit meant for
hardware).

## The version string

v1.0.4's kernel banner said `v1.0.3-123-g1ec37307` and its `cosmo-upgrade`
package `1.0.3-123`: the release build saw its own tag as a lightweight
one and named the previous release. This release's banner and
package say 1.0.5, and the release workflow now refuses to publish when
the kernel's build id, the release files, the package version or these
notes name anything other than the tag.
