# CosmoOS 1.0.12

## ssh after reboot

**Every service starts at every boot.** Before 1.0.12, `/run/svc` was on
the root disk and outlived the boot. When a pid recorded in it belonged to
a different process at the next boot, `svc` said `svc: dropbear is
already running` and never started dropbear, so ssh was refused until
the file was removed by hand.

- init mounts a fresh `/run` (a ramfs) at every boot, so nothing left
  there by an earlier boot is seen.
- A pid file now records its process's start time. `svc` takes it as
  the service's only if that process is the service's own supervisor and
  was started at that time.
- `svc stop` signals a service's process only if it is still that
  service's.

## Upgrades reach both mirror disks

**On a mirrored root, `cosmo-upgrade` writes every disk's ESP.** An
upgrade, `--fetch`, `--rollback` or `--repair` writes the new boot set to
the ESP of the disk the system booted from, then copies it to the other
disk's ESP and reads it back:

```text
cosmo-upgrade: the ESP on vda1 is ahci0p0p1's (44032 sectors written)
```

Either disk alone then boots the new release.

- If a copy is missing during an upgrade, `cosmo-upgrade` says so and
  upgrades the disk that is there.
- When the missing disk is back, the boot says its ESP lags and names the
  command:

  ```text
  cosmo-upgrade: the ESP on vda1 is not ahci0p0p1's (its set 4360a4d314f4, the booted 05822dd894bd): run cosmo-upgrade --repair to bring it up to date
  ```

  `cosmo-upgrade --repair` brings it up to the booted one.
- `cosmo-upgrade --esp-check` runs that comparison on demand.

See [Upgrades reach both disks](../guide/mirrors.md#upgrades-reach-both-disks)
in the guide.

## Fixes

- **A release candidate's run checks the notes its release will
  publish.** v1.0.11's first tag failed on notes an rc had not checked;
  the rc's run now builds and checks the final release's notes too.

## Upgrading from v1.0.11

`cosmo-upgrade --fetch v1.0.12`, reboot, then `pkg update && pkg
upgrade`. The upgrade takes a boot environment, so `cosmo-upgrade
--rollback` returns the root and the boot set as they were. The pool's
format does not change.

The upgrade to 1.0.12 is done by 1.0.11's `cosmo-upgrade`, which writes
only the booted disk's ESP. On a mirrored root, the first boot of 1.0.12
names the other disk's ESP as lagging. Run `cosmo-upgrade --repair` once
to bring it up to date.

Tested:

- On every change, on both architectures, beside the release tests:
  - `make test-install` reboots the installed system with stale pid
    files under the old root's `/run`, then requires every service to
    have started.
  - `make test-mirror`'s new stage on a mirrored install:
    - upgrade, then boot from the second disk alone into the new
      release;
    - upgrade with that disk absent, then repair it;
    - roll back, then boot from the second disk alone.
- On a Parallels virtual machine, upgraded from v1.0.11 to v1.0.12-rc1
  before this release was tagged, with ssh reached after reboots with
  no cleanup by hand. See [Tested platforms](../guide/platforms.md).
