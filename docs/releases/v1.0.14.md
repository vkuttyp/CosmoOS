# CosmoOS 1.0.14

## A large compressible file no longer loses data

**Every release before this one could lose the end of a large file
without saying so.** cosmofs compresses every regular file it can (LZ4,
since format 6). Each compressed 32 KiB record is a run of its own, and
a file's map holds at most 4096 runs, so a compressible file met that
limit at about 128 MiB. The limit was met when the pages were written
back, not when they were written. `dd` and `cp` were told nothing for
the data past it, every write-back of those pages failed, and the pages
were lost while the file's size still counted them:

```text
[ WARN] vfs: 512 dirty page(s) of inode 2 on cosmofs lost: write-back failed (-27)
```

On v1.0.13, on a 1 GiB pool, the largest compressible file was 124 MiB.
On v1.0.14 it is 1016 MiB, the pool full.

- Past three quarters of the limit, new records are written
  uncompressed, so they merge into long runs and the file can grow to
  the size of its pool.
- A write that would still cross the limit (a file `fsync`ed after
  every 32 KiB, or one with a hole between every two records) is
  refused when it is made, with `File too large`. Nothing already
  written is lost.
- No format change. v1.0.13 reads what v1.0.14 writes, and `cosmo-upgrade
  --rollback` works as before.

**Check your files.** A compressible file (text, logs, programs, a disk
image of them) larger than about 128 MiB, written on any release before
this one, may have lost what came after that point, though its size is
the size that was written. Copy such
files again from where they came from. Files that do not compress
(already compressed, or encrypted before they were written) were not
affected.

## A writer past memory, or past the disk, is told so

Before this release, dirty pages waiting for write-back had no limit
except memory, and a file's space was not charged until write-back.

- **Memory.** Writing 512 MiB with no `sync` on a 256 MiB machine left
  the shell unable to start a program (`sh: cat: Out of memory`). Now
  at most an eighth of memory is dirty: a writer at that limit writes
  its own file back, then waits, so other programs keep running.
- **Space.** `dd` filling a 256 MiB root was told `No space left on
  device` only after 178 MiB, and 2010 of its pages had already been
  lost at write-back. Now each page is charged against the free space
  when it is written, so the write that does not fit is refused with
  `No space left on device` and nothing is lost.

## Upgrading from v1.0.13

`cosmo-upgrade --fetch v1.0.14`, reboot, then `pkg update && pkg
upgrade`. The format is unchanged, and `cosmo-upgrade --rollback` returns
to 1.0.13.

Tested:

- On every change, on both architectures: `make test-large` writes the
  largest compressible file a 1 GiB pool holds (1016 MiB on x86-64,
  1012 MiB on AArch64) with no page lost, and v1.0.13's kernel, booted
  from its boot environment, reads it back. `make test-fill` writes 512 MiB with no `sync` on a
  256 MiB machine with nothing killed, then fills the root with one `dd`
  to `No space left on device` with no page lost.
- On two Parallels virtual machines, one plain and one with an
  encrypted root, upgraded from v1.0.13 to v1.0.14-rc1 before this
  release was tagged. See [Tested platforms](../guide/platforms.md).
