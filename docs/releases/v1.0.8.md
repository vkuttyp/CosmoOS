## Upgrades can be fully undone

From this release on, `cosmo-upgrade` takes a snapshot of the root
before it writes anything -- a **boot environment**, `be-<release>` --
and pairs it with the boot set it ran on, in `\cosmo\be` on the system
partition. `cosmo-upgrade --rollback` then returns both halves: the boot
set at once, and the root -- packages, `/etc` and the base system,
byte for byte as they were -- at the reboot it starts itself.

- **What you wrote is kept.** Files added or changed under `/root`,
  `/home` and `/var/log` since the environment was taken are copied,
  before any service starts, into `/var/lib/cosmo/rollback/<the replaced
  tree>/`. If they cannot all be copied, the replaced tree stays held
  (it cannot be deleted) and the next boot tries again.
- **The replaced tree is an environment too**: rolling back again goes
  forward to it. `cosmo-upgrade --list` shows the environments and the
  set each one pairs with; the newest two are kept, and `--prune`
  deletes older ones.
- **A crash at any step boots.** The intent is recorded in `\cosmo\be`
  before anything moves; whatever the machine boots afterwards -- the
  newer kernel on the older root, or the older kernel on the newer one --
  `cosmo-upgrade --repair` finishes what was meant. `--status` says when
  a repair is needed.
- **Refused, with nothing written**: an upgrade on a root without room
  for the environment (the sentence names what is needed and what is
  free), while a rollback of the root is pending, and when the root is
  not the current set's.

**There are no environments for v1.0.7 and earlier, and the upgrade to
v1.0.8 takes none.** Those releases keep no snapshots, and their
`cosmo-upgrade` refuses a system partition that records environments,
which a rollback to one of them would leave behind. The first upgrade
that can be fully undone is the one made *from* v1.0.8. Rolling back
from v1.0.8 to v1.0.7 returns the boot set and the base system, as
before; packages `pkg upgrade` changed stay changed.

## Package transactions

`pkg install`, `upgrade`, `remove` and `rollback` are each one
transaction: `pkg` snapshots the root first and deletes the snapshot when
it is done. If the machine stops in the middle -- `pkg install a b` with
`a` in place and `b` not -- the next boot rolls the root back to the
moment the transaction began, and reboots once to do so. `pkg` refuses
before changing anything when the root lacks the room.

**`pkg rollback NAME`** returns one package to the version installed
before the current one, with its files; the last two versions of each
package are kept in `/var/cache/pkg/kept`.

While `\cosmo\prev` holds v1.0.7 or older -- right after upgrading from
it -- `pkg` takes no snapshot and says so (`no transaction: ...`): the
first snapshot raises the root to cosmofs format 12, which those kernels
cannot mount. The same rule keeps the upgrade to v1.0.8 from taking an
environment.

## Snapshots and rollback from the shell

`cosmo-snap` takes snapshots of the installed root, lists what each one
holds alone, shows what changed since (`cosmo-snap diff`), rolls the
system back to one, and makes writable clones. A rollback keeps the tree
it replaces as a snapshot, applies at the next mount, and holds that
snapshot -- it cannot be deleted -- until the boot completes. The guide's "Snapshots and rollback" page has the steps.

## Fixes

- **A write-back that fails partway keeps what it wrote.** On a full
  disk, a file closed while its last write-back failed could leave
  blocks no file named (`fsctl check`: leaked) and, for a file
  overwritten in place, free blocks the file still named. The inode is
  now stored after every write-back, failed or not.
- **A foreground job owns the terminal from its first instruction.** A
  shell started from `cosmo-sh` could stop itself with `SIGTTIN` before
  `cosmo-sh` handed it the terminal.

## Known

`pkg install -f NAME=VERSION` to an older version says it is
"upgraded"; it is a downgrade (backlog PKG-9).

## Upgrading from v1.0.7

`cosmo-upgrade --fetch v1.0.8`, reboot, then `pkg update && pkg
upgrade`. No boot environment is taken by this upgrade (above); the
next one is.

Tested: on every change and on both architectures, `make test-upgrade`
(the published v1.0.3 upgraded to this build and back; then
`test-pkgtx`'s killed transactions and full root, and `test-be`: an
upgrade, `pkg upgrade` and a changed `/etc` rolled back byte for byte,
the operator's files kept, and a crash after each step), and `make
test-snapshot` (a broken system rolled back, three kills during a
rollback, a clone).
