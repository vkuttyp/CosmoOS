## If you rolled back and forward on v1.0.8: run `cosmo-upgrade --repair`

On v1.0.8, `cosmo-upgrade --rollback` to v1.0.7, then v1.0.7's own
`cosmo-upgrade --rollback` forward again, left the root's record of its
base system (`/var/lib/cosmo-upgrade/root-set`) naming v1.0.7's set.
v1.0.8 trusted that record, so it refused every later upgrade (`the root
holds another set's base system than the current set's (a rollback half
done): cosmo-upgrade --repair first`), and its `--repair` found nothing
to do.

**On such a system, run CosmoOS 1.0.9's `cosmo-upgrade --repair` once,
from the release's signed package, then upgrade as usual:**

```text
cosmo$ mkdir /tmp/up && cd /tmp/up
cosmo$ wget -q https://vkuttyp.github.io/CosmoOS/releases/v1.0.9/cosmoos-x86_64-cosmo-upgrade.cpk
cosmo$ pkg install -n ./cosmoos-x86_64-cosmo-upgrade.cpk
cosmo$ tar -xf cosmoos-x86_64-cosmo-upgrade.cpk sbin/cosmo-upgrade
cosmo$ ./sbin/cosmo-upgrade --repair
cosmo-upgrade: the root's record named the previous set's (v1.0.7, ...) base system, but its files are the current set's (v1.0.8, ...): record corrected
cosmo$ cd / && cosmo-upgrade --fetch v1.0.9
```

(`aarch64` in place of `x86_64` on an ARM machine.) `--repair` corrects
the record from the root's files and changes nothing else. A system that
never rolled back needs none of this: `cosmo-upgrade --fetch v1.0.9`.

From this release on, the record is checked, not trusted. Which set's
base system the root holds is told from the root's own files: the files
each kept boot set's `boot.tar` puts under `/bin`, `/sbin`, `/usr`, `/lib`
and the package repository, byte for byte (`/etc` is yours and is not
looked at). An upgrade is refused only when those files are the previous
set's -- a rollback really half done -- never on the record alone. When
the record disagrees with the files, `cosmo-upgrade --list` says so and
names both, and the upgrade, a rollback and `--repair` correct it. The
record now also names the release it describes and the set it was
written from, so a record an older `cosmo-upgrade` left behind is named
as such. `cosmo-install` writes it at install.

## Fixes

- **A long console write no longer stops a CPU's interrupts.** The
  console held its lock, with interrupts off, for the whole of one write
  while every output device drew it. `dmesg` prints the kernel log in one
  32 KiB write; drawn on the screen console, that kept one CPU without
  interrupts for over a second, and another CPU waiting on it for a TLB
  invalidation panicked (`mmu: TLB shootdown ... acknowledged by 2 of 3
  CPUs`). A write is now passed on a line at a time. A virtio console
  whose device stops answering still costs one 200 ms wait per write.
- **`pkg` says a downgrade is a downgrade.** `pkg install NAME=VERSION`
  to an older version said `NAME will be upgraded from 1.1 to 1.0`; it
  says `downgraded`.

## Upgrading from v1.0.8

`cosmo-upgrade --fetch v1.0.9` (after `--repair` as above, if you rolled
back and forward), reboot, then `pkg update && pkg upgrade`. This upgrade
takes a boot environment, so `cosmo-upgrade --rollback` returns the root
and the boot set as they were.

Tested: on every change and on both architectures, `make test-upgrade`,
whose `test-be` now includes the published v1.0.7 upgraded to this
build, rolled back, rolled forward by v1.0.7's own `cosmo-upgrade`, and
upgraded again; and on a Parallels virtual machine in that state, which
`--repair` cleared before it upgraded to this release.
