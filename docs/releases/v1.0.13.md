# CosmoOS 1.0.13

## An encrypted root

**`cosmo-install --encrypt` encrypts the root, and the machine asks for
a passphrase at every boot.** File contents and directory names are
ciphertext on the disk. The pool's own records (inodes, maps, bitmaps,
checksums, snapshots, superblocks, labels) carry a keyed tag, so a
change made to them without the key is refused rather than believed.

```text
cosmo$ cosmo-install --encrypt vdc
new passphrase:
new passphrase again:
cosmo-install: slot 0 sealed with the passphrase (argon2id 65536 KiB, 3 passes: 2.20 s)
```

At the next boot, before the root is checked or mounted:

```text
passphrase for cosmo-root:
cosmo-key: cosmo-root unlocked with slot 0 (argon2id 65536 KiB, 3 passes: 1.03 s)
```

- The prompt is on the display and the serial line, and nothing is
  echoed. Three wrong passphrases restart the machine with nothing
  mounted.
- The passphrase seals a random master key with Argon2id: 64 MiB and
  three passes per guess, a fixed cost that takes about a second under
  QEMU and 0.16 s on an Apple-silicon Parallels VM. `cosmo-key change
  --passes N --memory KIB` raises it. A pool has eight key slots:
  `cosmo-key add`, `change` and `remove` manage them without touching a
  file.
- `--key-file` puts a random key in slot 0, on the EFI System Partition,
  and the passphrase in slot 1, so the machine boots unattended. The
  ESP is not encrypted: this does not protect a disk that leaves the
  building.
- `--mirror DISK2` makes both disks one pool with one key.
- Snapshots, rollback, boot environments, mirrors, resilvering, scrub
  and `fsck.cosmofs` work on an encrypted root.

See [Encrypted root](../guide/encrypted-root.md) in the guide, including
what it does not protect.

## Larger encrypted files

A file on an encrypted pool was limited to 252 MiB. A file that passes
that gets a second level of checksum index, so the limit is now 125 GiB
encrypted and 1000 GiB plain. The first such file raises the pool to
format 14, as an encrypted root starts.

## Fixes

- **A damaged member table is refused.** The table of a pool's disks was
  read with only its magic, kind and address checked, so damage to the
  rest of it went unnoticed. It is now checked like every other block.

## Upgrading from v1.0.12

`cosmo-upgrade --fetch v1.0.13`, reboot, then `pkg update && pkg
upgrade`. A root installed without `--encrypt` keeps its format, and
`cosmo-upgrade --rollback` returns to 1.0.12 as before. An existing root
cannot be encrypted in place: install to a new disk with `--encrypt` and
copy the data across.

A pool at format 14 (an encrypted root, or one holding a file past the
old limit) cannot be read by 1.0.12 or older, and `cosmo-upgrade`
refuses to roll it back to them.

Tested:

- On every change, on both architectures: `make test-encrypt` installs
  encrypted with the harness typing the passphrase, refuses a wrong one
  and restarts after three, finds no plaintext on the disk, refuses each
  kind of metadata block forged with its old checksum recomputed, opens
  a second slot and a key file, writes and reads back a 1 GiB file, then
  runs the snapshot, fsck, mirror, package and boot-environment tests
  again on an encrypted root.
- On a Parallels virtual machine, upgraded from v1.0.12 to
  v1.0.13-rc1 and then -rc2 before this release was tagged; and a
  second one, installed encrypted from -rc1, unlocked at its console,
  and upgraded to -rc2 on its encrypted root. See
  [Tested platforms](../guide/platforms.md).
