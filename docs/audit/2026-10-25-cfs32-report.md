# CFS-32: a write past the run bound refused at the write, and a compressible file the size of its pool, 2026-10-25

The second of v1.0.14's PRs. The brief: CFS-32 is a blocker. First
containment (1a): a write past the run bound is refused at the write,
`-EFBIG` with nothing dirtied, never at the commit, and no path may leave
dirty pages that can never be written back. Then the bound itself (1b),
with no on-disk format change and v1.0.13 still able to read what this
build writes (rollback to `be-v1.0.13` keeps working).

## Scope and baseline

Main at `75e1e15f` (#453, be-space attributed), CI run 40140311805
green on every job.

A compressed record is one run of its own (a compressed extent's 16-bit
count and 8-bit length, the compressed length not stored, so it neither
merges nor is merged into), and an inode's map holds at most
`CFS_MAX_EXTENTS` (4096) runs. A file LZ4 compresses therefore reached
the bound at about 128 MiB, and the bound was met at write-back: the
writes were taken into the page cache, every write-back of them failed
`-EFBIG`, and the pages were lost with the vnode while the file's size
still counted them (backlog CFS-32).

Measured on the published v1.0.13, before anything here (`make
test-large LARGE_BEFORE=1`, x86-64): on a 1 GiB pool, 4 MiB chunks of
the system's own programs each written with `dd ... conv=fsync` until
one fails:

    before: v1.0.13's kernel: the largest compressible file on a 1024 MiB pool: 124 MiB
    (31 chunks of 4 MiB, 12 s); the next chunk's dd: 'dd: /mnt/m/fill: File too large';
    the file's size 128 MiB; pages lost: [('512', 'write-back failed (-27)')]

## 1a: refused at the write

The design (vfs `design.md`, "Refused at the write"; cosmofs
`design.md`, "The run bound, charged at the write"; invariants V39,
CF33). A new vnode operation, `dirty_check(vn, index, dirty)`, is asked
before a clean page becomes dirty, in `pagecache_write`, the shared
mapping's write fault and `pagecache_put_page`; a refusal refuses the
write before a byte is copied. cosmofs charges each dirty page two runs
(a write-back is one `set_extent`, which adds at most two), so a page may
become dirty while

    runs + 2 x (dirty pages + 1) + CFS_TRUNC_ADDS <= CFS_MAX_EXTENTS

`pagecache_write` holds the vnode lock, so on `-EFBIG` with dirty pages
of its own it writes them back once and asks again: the charge for what
is dirty becomes what it cost. `runs` comes from the map as last stored
(`fs->map_stores`, `note_runs`), read again from the chain only when
another inode's store came between. A truncate writes the dirty pages
first when its own additions could reach the room they were charged
for. The same check refuses a page past a 32-bit logical block, a page
of a snapshot's tree (`-EROFS`) and any page once the transaction is
abandoned (`-EIO`). Under `CONFIG_DEBUG` a write-back that fails
`-EFBIG` or `-EROFS` anyway panics naming the inode and the page
(`stuck_page_check`).

The failing test, first: `cosmofs-extent-bound`, a sparse compressible
file (one record at every other record's place, so no two merge) on a
mount whose bound the test seam lowers to 64 runs. On the unfixed tree:
`100 of 100 records accepted`, then `288 dirty page(s) of inode 2 on
cosmofs lost: write-back failed (-27)`. Fixed: 54 accepted, the next
write `-EFBIG`, `file_sync` 0, no write-back error, no page dropped, the
file's size after a remount ending at the last record taken, every
record reading back, the check clean.

One path is known to cost more than its charge, and stays the debug
panic's to name: a page in a compressed record that leaves the record
incompressible has the record written again as eight plain blocks, and on
free space of single blocks only those are eight runs (seven more for a
page charged two). `cosmofs-extent-rebuild` builds it as far as a test
can (records of six noise pages and two zero pages, one zero page made
noise, the pool's free space cut up by deleting every other one-block
file): the map went from 29 runs to 46 over 13 rebuilds, 1.3 more each,
within the charge, and the test's writes were refused at the write near
the bound with everything else written back. Backlog CFS-39.

## 1b: plain past three quarters of the bound

The owner's direction: not a format change (rollback to `be-v1.0.13`
must keep working; v15 later, with CFS-35 and multi-record extents);
first verify on the v1.0.13 tag, checked out, that its `extent_valid`
accepts an uncompressed run of any count and that contiguous uncompressed
records merge. Both hold on `v1.0.13` (checked out at
`scratchpad/wt-v1013`, 2026-10-24): `extent_valid` bounds only a
compressed run's count and length, the checker has no count bound for a
plain run, and `extents_merge` joins two plain runs adjacent on the disk
and in the file.

The design (cosmofs `design.md`, "Plain past three quarters of the
bound"). Once an inode holds `CFS_RAW_AT_PERCENT` (75) of the runs it may
have, `cfs_writepages` writes a new record plain (`record_compresses`),
as one run of eight blocks allocated together (`plain_run_write`), which
then merges into the plain run before it. A record that replaces a
compressed record still compresses (it takes that record's run rather
than adding one), and a truncate or rewrite that takes the inode under
the mark brings compression back.

The failing test, first: `test-large` (`tests/boot/large_test.py`),
the one the brief names. A self-test came with it, `cosmofs-extent-raw`
(200 compressible records in order under a seam bound of 64), and it
does not fail without the policy, though I first wrote that it did. The
probe's `--old` run showed it (both arches): under so low a bound, the
write's charge (CF33) cuts records into plain blocks, which merge, from
about the same point as the mark. Both trees ended at 53 runs, even with
a commit every 16 records. It stays as the policy's coverage (a rewrite
stays compressed, a truncate below the mark compresses again), and the
probe runs `test-large`. In `test-large`, the published
v1.0.13 installs itself and upgrades to this build with its own
`cosmo-upgrade`, which takes `be-v1.0.13` first; this build fills a
1 GiB pool with one compressible file chunk by chunk and writes a 1 GiB
compressible file on a 1.5 GiB pool, both checked clean; after a reboot
both read back the same, and `cosmo-upgrade --rollback --no-reboot`;
then v1.0.13's own kernel, booted from `be-v1.0.13`, mounts both pools,
reads both files back (the 1 GiB one by SHA-256, the filled one chunk by
chunk) and checks both clean.

    large: LARGEST 1016 MiB compressible on a 1024 MiB pool
    test-large: write: the largest compressible file on a 1024 MiB pool: 1016 MiB (254 chunks of
    4 MiB, 168 s); the 1024 MiB file written whole in 424 s; both pools clean
    test-large: remount: both files the same after a reboot, both pools clean; rolled back
    test-large: old: v1.0.13's kernel, booted from be-v1.0.13: both pools mount, both files read
    back the same (the 1 GiB file by SHA-256, the filled one chunk by chunk), both checks clean
    test-large: PASS in 2435.5s

Without the policy (its commit reverted, 1a kept; x86-64):

    test-large: FAIL: every chunk of the 1 GiB file: no line matching '^wrote=256$'
    guest: wrote=36; /mnt/l/big 154079232 bytes; no dirty page lost

**The largest compressible file on a 1 GiB pool: 124 MiB before (v1.0.13,
with 512 dirty pages lost), 1016 MiB after, the pool full rather than
the bound reached** (x86-64; docs/guide/limitations.md). With 1a alone,
the 1 GiB file stops at 144 to 148 MiB, refused at the write.

One loss remains in `test-large` on this branch, and it is not CFS-32's.
The fill ends when the pool is full: the 255th chunk's `dd` fails, and
that chunk's pages are lost at write-back with `-ENOSPC`. That was 167
pages on x86-64 and 88 on AArch64, against 254 chunks kept and read back.
That is MEM-9's ENOSPC half, a write taken that the pool cannot hold,
fixed by the next PR, which also makes `test-large` fail on any lost
page. The probe counts `-EFBIG`'s losses and reports these.

**What still meets the bound.** The brief asks that 1a's `-EFBIG` still
be reachable by a file that defeats the policy, or that I say none can
exist. Such files exist: records merge when they are written back
together, and the first record of the next write-back did not land next
to them in the self-test (the allocator's hint is shared with the
commit's own blocks, a likely reason, not checked), so a writer that
commits after every record past the mark adds a run per record, as
compressed records did. `cosmofs-extent-raw` with a `file_sync` after
each record showed it: one run per record past the mark, then `-EFBIG`
at the write. A sparse file's records never touch, and
`cosmofs-extent-bound` is that file: refused at the write.

## CFS-36: the per-commit cost, measured

The brief puts CFS-36 in this unit only if 1b's measurement shows the
per-commit cost is the run map or checksum index written whole, and the
fix is writing what changed. Measured with a temporary count, not
committed, of the metadata blocks each commit wrote by kind (the commit's
dirty-buffer loop), and the guest's clock every 32 MiB of `test-large`'s
1 GiB file (x86-64, release, 2026-10-25):

| file | s per 32 MiB | commits | per commit: extents | bitmap | checksum | index | inode | other |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 64 MiB | 3 | 17 | 3.3 | 1.0 | 1.0 | 0.5 | 0.5 | 3.1 |
| 128 MiB | 4 | 24 | 8.7 | 1.0 | 1.0 | 0.7 | 0.7 | 3.3 |
| 256 MiB | 6 | 24 | 13.0 | 2.0 | 1.3 | 1.0 | 1.0 | 4.0 |
| 512 MiB | 7 | 26 | 13.5 | 2.5 | 1.3 | 1.0 | 1.0 | 3.9 |
| 768 MiB | 9 | 8 | 15.0 | 4.0 | 2.0 | 1.0 | 1.0 | 4.0 |
| 1024 MiB | 8 | 8 | 15.0 | 3.0 | 2.0 | 1.0 | 1.0 | 4.0 |

Each commit does write the run map whole, but with the write policy the
map stops at about 15 blocks once the file is past the mark, and a commit
writes about 24 metadata blocks in all against 8192 data blocks per
32 MiB: flat past 256 MiB, while the time per 32 MiB still rises and the
commits per 32 MiB fall from 24 to 8. The cost is therefore not the map
or the checksum index written whole, and CFS-36 stays in the backlog
with this measurement. The next candidate is CPU: each record's
write-back loads and stores the whole map in memory (`extents_load`,
`extents_store`), proportional to the file's runs. The full table is the
backlog line's.
